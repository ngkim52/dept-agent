# 001. 아키텍처 (v0.1 초안)

## 1. 전체 구성 (텍스트 다이어그램)
```
┌─────────────────────────────────────────────────────────┐
│  [웹 브라우저]  로그인 / 질문 / 자료 업로드 / 답변       │
└────────────────────────┬────────────────────────────────┘
                         │ HTTPS
┌────────────────────────▼────────────────────────────────┐
│  [웹 앱 서버]  (Next.js 등, Docker 이미지로 배포)          │
│  ├─ 인증/세션 레이어 (사용자 로그인, JWT/쿠키 세션)       │
│  ├─ 문서 업로드 → RAGFlow API 호출                     │
│  ├─ 대화 API → 에이전트 엔진 호출 (스트리밍)             │
│  └─ DB (사용자/부서/대화/권한) — SQLite/Postgres    │
└───────────────┬───────────────────────┬───────────────┘
                │                      │
                ▼                      ▼
   ┌──────────────────┐   ┌──────────────────────┐
   │ [에이전트 엔진]     │   │ [RAGFlow 서버]        │
   │ pi-agent-core      │   │ (별도 운영, HTTP API)  │
   │ ├ 상위 에이전트      │   │  - 데이터셋(부서별)     │
   │ └ sub-agent 형태로  │   │  - 문서 파싱/청킹      │
   │    부서장 페르소나   │   │  - 검색(retrieve)     │
   │ (LLM: DeepSeek)    │   │                     │
   └──────────────────┘   └──────────────────────┘
```

## 2. 처방 같은 설명 (핵심 아이디어)
- **질문 흐름**: 사용자 질문 → (문서가 있으면) RAGFlow에서 검색 → 검색 결과를 컨텍스트로 부서장 에이전트가 답변.
  "통합 검색(RAG) + 페르소나 판단" 이 핵심.
- **업로드 흐름**: 사용자 업로드 → 부서 데이터셋에 문서 추가 → 파싱 완료 후 검색 가능.
- **부서장 페르소나**: 에이전트 엔진에서 sub-agent = 페르소나. 시스템 프롬프트 + 업무 규칙 + RAG 검색 툴로 구성.
- 응답은 가능하면 스트리밍 (pi-agent-core subscribe 이벤트 지원 확인).

## 3. 에이전트 엔진 (v1 실구현: 방안 A — 반영 2026-08-21)
- **v1 실행 방식: `@earendil-works/pi-ai`를 직접 사용하여 `models.stream(model, {systemPrompt, messages})` 호출** (부서 페르소나 = systemPrompt 교체).
  - `src/lib/agent/llm.ts`(모델 프로바이더) + `src/lib/agent/engine.ts`(RAG 청크 주입·히스토리 변환·text_delta 콜백) 구성.
- **방안 B(pi-agent-core 상위 에이전트 + sub-agent, RLM 스타일)는 2차(계리팀 등 다중 부서·복합 판단)에서 도입 재검토** (`docs/features/f004` 방침과 동일).
- RAG 검색은 질문 직전 부서 데이터셋에서 실행 → `<<<RAG_CONTEXT>>>` 블록으로 컨텍스트에 삽입.
- 이벤트: `start / citations / text_delta / done / error` (SSE).

## 4. RAG 데이터셋 구조 (확정 방향)
```
[RAGFlow 데이터셋]           = 접근 경계 (부서 단위)
├─ 보험금심사기획 데이터셋    ← 1차 대상 (MVP)
└─ 계리 데이터셋             ← 2차 (추가 예정)
（필요 시 공통 데이터셋: 업무규정/공통기준 → 전사 공개 여부는 별도 결정）
각 데이터셋 안에 부서 자료 문서(파싱 완료 후 검색 가능)
```
> 사용자 문서 업로드 = 소속 부서 데이터셋에 등록.
> 질문 시 retrieval은 "내 부서 데이터셋만" 조회 (권한 강제).

## 5. 기술 스택 (확정 2026-08-20 — 에이전트 엔진 연동 우선)
| 계층 | 선택 | 이유 |
|---|---|---|
| 웹 프레임워크 | **Next.js (App Router, TS)** | 풀스택·SSE 라우트 핸들러·바이브 코딩 친화 |
| UI | Tailwind CSS | 빠른 화면, 바이브 프롬프트에 유리 |
| DB (MVP) | **SQLite + Drizzle ORM** | 단일 파일·Docker 배포 단순. 운영 시 Postgres 전환 가능 |
| 인증 | 자체 구현 (bcrypt + httpOnly 쿠키 세션) | 회원가입/도메인 제한/부서 선택 커스텀에 적합 |
| 에이전트 엔진 (v1) | **@earendil-works/pi-ai 직접 `models.stream`** (pi-agent-core는 2차 도입) | MVP 단순화, 페르소나=systemPrompt 교체 (방안 A) |
| LLM | **deepseek-v4-flash** (LiteLLM 게이트웨이 `https://litellm.ax-demo.com/v1`, OpenAI 호환 API → pi-ai 커스텀 모델, `LLM_API_KEY`) | 확정 |
| RAG | RAGFlow REST API 클라이언트 모듈 | 외부 서버, 부서 단위 데이터셋 |
| 스트리밍 | SSE (Next Route Handler + ReadableStream) | 확정된 응답 방식 |
| 배포 | Docker 단일 이미지 (Node 22) + SQLite 볼륨 | MVP 단순화. RAGFlow는 별도 서비스 |

## 6. SSE 질문-응답 흐름 (확정 방향)
```
POST /api/chat/messages (사용자 메시지)
  → [서버] 부서 판별(가입 부서) 
  → RAGFlow retrieval (부서 데이터셋만) → 근거 청크
  → pi-agent-core(piense persona systemPrompt) → 스트림
  → SSE events: {type:'delta', content} | {type:'citations'} | {type:'done'}
  → 클라이언트 렌더 (대화 저장은 서버에서)
```

- 배포: Docker 단일 이미지(standalone, Node 22) + SQLite 볼륨(`DATA_DIR=/app/data`) + docker-compose 예시 (저장소 루트)
